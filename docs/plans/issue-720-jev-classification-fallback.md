q: Is the defect only OCBC wording, or a shared flow? | a: shared. `_resolveMovementToOutput` hardcodes `Misc` for every incoming movement with no counterparty (`orchestrator.js:1126`), the Phase 2 merchant tier is skipped for any prepopulated payee (`orchestrator.js:2509`, `!output.payee_name`), and `_handle_resolve_merchant` (`tools.js:1974`) returns `Misc` after a memory miss for every caller (outgoing merchants included). q: Where does the exact reference get lost? | a: `extractEmailContent` collapses all whitespace (`extractors.js:~75`), so `field()` in `bank-movement.js:93` (`[^\n]+`) reads from `Reference:` to the end of the flattened body. The email's own line breaks are the only reliable field boundary, so the plan keeps a second, line-preserving extraction as evidence and uses it to bound the reference. The existing flattened text still feeds the parser and Phase 1 unchanged.
q: Which Jev request shape? | a: the documented System One shape, the same one the dev-loop driver already uses: `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer $JEV_API_KEY` and `{model: "jev-latest", state, questions}`. A `choice` question answers with `choice`, per-option `probabilities` and `confidence`; a `noul` question answers with a probability under `noul`. Choice takes 1 to 255 options. Answers are read from `answers` when present, else from the top level, because the vendor docs show both.
q: How do "best match, runner-up, confidence, supporting evidence" map onto typed answers? | a: question 1 is a `choice` over every eligible payee plus one explicit "none of the listed payees" option: best = `choice`, runner-up = the next highest probability, confidence = `confidence`. Question 2 is a `noul` asked about the winning payee ("does the email text itself state or directly imply this payee, beyond general knowledge of the label?"): supporting evidence = that probability. The matched descriptor is kept as the human-readable evidence in the notification.
q: What is accepted? | a: the choice must be exactly one eligible payee (not the none option), `confidence >= 0.85`, `probabilities[best] - probabilities[runner_up] >= 0.30` (a missing probability map rejects), and the evidence `noul >= 0.80`. Anything else, an HTTP error, a timeout, a malformed answer, a missing `JEV_API_KEY`, or more than 255 eligible payees leaves `Misc`. The thresholds are constants in one place and are covered by boundary tests (just above and just below each). They are initial values to calibrate, not ground truth; a model score alone never books anything the validation rejects.
q: Which payees are eligible? | a: every payee returned by `fetch_context`/`/payees` except account-transfer payees (`transfer_acct` set), `Misc`, `Starting Balance`, blanks, and any name that appears more than once case-insensitively (an ambiguous name fails `AMBIGUOUS_PAYEE` at insert). `OCBC 360` is a transfer payee, so it can never be chosen. `Bank Interest` stays eligible. Jev's answer is re-validated against that list by exact name after the call.
q: Can email content steer the model or the tools? | a: it can bias a classification and nothing else. The call is a typed classifier with no tools; the email sits between markers in the `state` string that declare it untrusted data; a literal closing marker inside the text is neutralised; the returned payee must be an exact eligible name; and no output is ever executed or learned automatically.
q: What is sent to Jev? | a: the line-preserved body text (capped at 6000 characters), the subject, the sender header value, direction and amount, and the descriptor. URLs are replaced by `[link]` (tracking links carry tokens) and digit runs of 8 or more are masked to their last four digits. No raw MIME headers, attachments, credentials or `.env` values are sent. The `evidence` argument is removed from `executeTool`'s `tool_exec` log line, and the new code logs only the payee names, confidences and a reason code, never the email text.
q: How does a deposit with no counterparty reach the resolver without breaking pinned behaviour? | a: the deterministic branch still returns `payee_name: "Misc"`, `_structured_movement: true` and the same amount/account/date, but now sets `merchant`/`raw_description` to the exact reference (when it is a single bounded line of at most 80 characters, otherwise `Unidentified deposit`), writes the reference into `notes`, and sets `_payee_unresolved: true`. Phase 2 clears the prepopulated `Misc` when that flag is set, so the existing memory, `resolve_merchant`, `Misc` tiers run. The empty-reference fixtures (`bank-movement.test.js:1090`, `production-incidents.test.js:230`) keep `Unidentified deposit`.
q: Does this weaken the internal-transfer and person holds? | a: no. The change is confined to the `!counterparty` incoming branch and the payee-tier guard. The person hold, the internal-transfer arm, the #680 named-credit arm, the PayNow identity branch, dedup, linking and account/date ownership are untouched, and Phase 2's transfer detection still runs on whatever payee the resolver returns. Transfer payees are excluded from Jev's options, and a memory-mapped payee keeps today's behaviour.
q: How is learning kept behind real user confirmation? | a: the pipeline never writes a fact for a Jev result. After the insert succeeds, Phase 3 stores a pending offer (descriptor, payee, budget) in a small file-backed store (`data/pending-learning.json`, 7-day expiry, 50-entry cap, random 6-character code) and the notification says "Remember '<descriptor>' as <payee>? Nothing is saved until you confirm with code <CODE>". Only a new `confirm_learning({code})` tool persists the exact `<descriptor> maps to <payee> payee` fact through the existing `learn_fact` path (so the account-identity validation still applies), and a new `decline_learning({code})` discards the offer. The Hermes skill is updated to call `confirm_learning` only after the user answers that offer, and never to `learn_fact` a Jev mapping directly.
q: Is that a hard boundary against a model confirming on its own? | assumption: no tool can prove a human typed "yes", because every tool is model-callable. The boundary is that persistence needs an unguessable, unexpired code that exists only in the notification delivered to the user and in the store, the pipeline never calls any learn path for a Jev result, and a wrong or reused code fails closed. ## Intent

An alert that cannot be classified deterministically is booked as `Misc` and loses what the email said. Issue #720 (an OCBC 360 `360 SAVE BONUS` deposit booked as `Unidentified deposit`) is one case of that. This change keeps the email as evidence, lets Jev choose among the user's real payees when memory has no answer, rejects weak answers, and learns a mapping only when the user confirms it.

## Change

1. `src/extractors.js`: `extractEmailContent(raw, password, { keepLines })`. With `keepLines` it collapses horizontal whitespace only and keeps line breaks; the default output is byte-identical to today.
2. `src/bank-movement.js`: export `exactReference(linesText, parsedReference)`, which reads the labelled reference from the line-preserved text and returns it only when the parser's value starts with it, otherwise the parser's value. `parseBankMovement` is unchanged.
3. `src/jev.js` (new): `eligiblePayees(payees)`, `scrubEvidence(text)`, and `classifyPayee(...)` implementing the request, validation and thresholds above. It takes an injectable `fetch` for tests.
4. `src/learning.js` (new): the file-backed pending-offer store (`offer`, `take`, `discard`).
5. `src/orchestrator.js`: build the evidence (line-preserved text, subject, sender) once in `_processEmailInternal` and attach it to Phase 1 output beside `_alert_id`; pass the line text to `_runStructuredMovement` to bound the reference; rework the `!counterparty` deposit branch as described; make Phase 2 clear a prepopulated `Misc` when `_payee_unresolved`, pass `evidence` to `resolve_merchant`, and carry the result's `source`, runner-up and confidence; in Phase 3 create the offer after a successful insert and append the confirmation text to the notification.

## Risks

- A confident but wrong Jev payee can still be booked for an outgoing merchant. Mitigations: exact-name validation, the three thresholds, the evidence question, and no learning. The user can correct it and decline the offer.
- `keepLines` for an HTML-only email cannot recover line breaks that cheerio already flattened; the deposit then keeps `Unidentified deposit` as its descriptor and Jev still sees the full text. Accepted; the upgrade is block-aware HTML text.
- Calibrating the thresholds needs real traffic. They are named constants for that reason.
